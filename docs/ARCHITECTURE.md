# SCAR 的分层和交接合同

`scar/cli.py` 负责命令分派。原生目标由 `scar/compiler/driver.py` 编排，已建模的 Python 区域由 `scar/compiler/pipeline.py` 编排。两条入口共用 `scar/compiler/contracts.py` 的交接类型和 C++20 后端。工件引用包含 `uri`、`schema`、`size_bytes`、`sha256`。原生运行把这些引用集中写入 `result.json` 的 `artifacts` 字段。

## 1. 前端

| 层 | 功能 | 输入 | 交接产物 |
| --- | --- | --- | --- |
| 源码接入 | 锁定源码字节和工作目录，为每个编译单元确定语言、方言和参数 | 入口、源码、编译配置 | 原生 `request.json`，Python 源码单元清单与 F0 字节记录 |
| 词法 | 识别 token，保留源码位置及无法识别的范围 | 锁定字节和方言 | Python F1 token、范围和覆盖记录。原生编译器内部消费 token |
| 语法 | 确定语法结构、嵌套范围和对应源码 | 源码、词法记录和解析配置 | Python F2 AST 和节点位置。原生编译器交出解析后的带位置记录 |
| 符号与类型 | 识别作用域、定义、引用、类型和调用位点 | 语法结构、编译参数和依赖声明 | Python F3 符号、作用域及绑定材料。原生编译单元交出 Clang 类型记录或 Fortran 编译语义记录 |
| 构图 | 将函数、基本块、循环回边和版本化值接入共享 IR | 每单元的类型、绑定和控制流事实 | `program.json` 中的 `ProgramGraph`，原生 `compiler-cfg.json`，以及 `graph-report.json` 中的源码锚点和缺口。用 `scar check-program` 独立检查持久化的图 |
| 跨单元绑定 | 将调用点关联到目标函数区域，记录间接调用、外部边界和入口可达性 | 原生编译器调用表、Clang 声明、图锚点和可用的 ELF 符号 | `call-links.json` 中的操作 ID、区域 ID 和证据来源 |
| 运行证据 | 对照实际调用与资源活动，记录静态分支中仍待判定的字段 | 有界 trace、调用锚点和资源观测 | 可重放的执行证据和绑定记录。Python 建图可消费这组材料 |
| 硬件建模 | 发布平台容量、拓扑和访问关系 | 本机 CPU、NUMA、内存、存储和设备库存 | `hardware/result.json` 及其引用的资源表。实测带宽和时长作为独立成本证据 |

源语言适配位于 `compiler/frontend/`。Python 源码规则与结构校验集中在 `analysis/static/lowering/`，原生适配使用 `frontend/clang.py`、`frontend/fortran.py` 和 `frontend/graph.py`。构图交出操作、数据与状态、跨单元调用、硬件和原始证据。整数 `switch` 通过有序分支和 SSA 参数建模，无后继调用块以 `NO_RETURN` 结束。结构校验、调用绑定及效果证明分别记录。

Python 的 F0 至 F3 由 `frontend/source.py` 按单元并行生成。同一单元从一份源码快照依次派生各层记录，各层分别发布原有类型、摘要和来源。F4 每个单元准备一次语义输入，供表达式、语句和根节点共用。对有显式编译参数的外部源码，同次构建的上下文、绑定、CPython 符号和拓扑按类型直接交接。独立重放重新验证各层输入和规则。`GraphBundle` 同时支持已降级的 `ProgramGraph` 和由 F4 声明目录保留的区域证据。

函数创建与来源核验共享源码编译结果和作用域索引，逐边复核常量槽位与端口。集合规则共享显示分段，分别投影到各自的图记录。调用链接的依赖视图使用与独立查询相同的工件路由初始化，读取预算由原链接会话负责。

类型图校验将操作、块、区域和值索引交给清理、恢复、驱动与协议检查。查找驱动目标直接沿操作所属块定位。角色传播、首个结果和待处理控制值按同一图复用。查询继承已通过校验的坐标，预算和查询结果仍由各自的查询会话记录。

原生前端通过 `SourceAdapter` 注册语言适配器。同一目标可以按单元显式选 `source_adapter`，并保留各自的标准、参数、编译器、解析器版本和源码摘要。适配器交付统一的控制流记录以及分离的类型与调用证据。为新语言生成独立 C++20 工程时还需提供经验证的源码转换或算子实现。

原生函数指针的有限目标集由 GCC SSA 的赋值和 φ 节点推导。地址起点须同时匹配 GCC 地址引用和 Clang 声明坐标。每个已绑定目标都进入可达性分析与跨语言链接检查。参数传入、内存加载等仍缺少来源的间接调用保留边界。

## 2. 中端

| 层 | 功能 | 输入 | 交接产物 |
| --- | --- | --- | --- |
| 图准入 | 核对图摘要、版本和 IR 结构，确定可分析的入口 | `GraphBundle` | 可读的 `ProgramGraph` 或已准入的区域以及分析范围 |
| 结构化简 | 根据依赖、作用域和效果判断合法改写，关联原操作和值 | 程序图、源码锚点和 Clang 类型证据 | `simplified` 图引用、SSA 拷贝传播清单与可重放的源码区间改写。图无改写时复用输入引用 |
| 资源与成本 | 把可实施选项、成本证据、核组、内存和时序约束表达成规划问题 | 图、改写清单、硬件引用和锁定用例 | `cost-observation.json` 与 `planning-problem.json` 中的 `PlanningProblem` |
| 选型和重放 | 以完工时间为目标选择合法的排程，并校验依赖和资源占用 | `PlanningProblem` | `plan.json` 中的执行计划以及验证结果 |

`compiler/middle/plan.py` 在同一次编译中直接消费前端的类型化图，派生一次 SSA 拷贝传播和源区间改写。独立进程从原图重算规则和简化图摘要，核对封存工件。有源码改写时，两份 C++20 产物在同一核上按用例交替测量，保留原始输出和样本。每个用例均须匹配原版，且改写版的实测区间均须低于保留版，方可采用改写。后端发布被选中的已测二进制并再次核对输出。没有源码改写时使用保留版。`scar plan --problem` 可独立重放，`--exact` 使用精确求解器。

原生 `rewrites.json` 同时记录入口效果证明。分析沿可达基本块及已绑定的直接或有限目标调用，汇总已覆盖的操作、虚拟内存读写和首个待证明操作。`CLOSED_BODY` 表示保留的 GCC SSA 源码体效果已覆盖。外部调用、未解析内存效果和未保留的异常控制按位置记录为 `OPEN_BODY`。进程启动和退出另属独立边界。后端从原图和调用证据重放，并核对计划声明的覆盖范围。

原生 CPU 准入与区域规划用同一硬件图读取器核对拓扑表。入口 CPU 从已验真的执行器、在线逻辑 CPU 与采集时许可范围取交集。单次事务复用这份集合，每次选型重新检查当前进程亲和性。独立交付进程重验硬件收据和引用的表。

CPU 成本探针共用 C++ 源码模板、编译与样本归约。两套 DAG 成本模型保留各自拟合规则和原数据格式，通过内部命令 `python -m scar.codegen.cpu_fused_cost_models --version 2` 或 `--version 3` 的 `calibrate`、`project` 子命令操作。旧探针按其生产者版本回读。

Python 的直接循环、跨函数组合循环和单数组递推由 `compiler/middle/python.py` 调度。中端根据循环证明和硬件快照发布 `schedule.json`，再发布锁定证明、特化和资源绑定的 `cpp20-lowering.json`。融合策略重放同时返回已验证的执行体，供后端直接使用。后端通过 `deliver` 消费类型化计划。一次编译中的源码准入与循环降级共用已打开的图会话。独立进程仍从原始证明和资源记录重放。

直接和组合循环通过共同的源码窗口投影交出参数路由。动作事实在合法性准入时派生一次，同步交给调度。组合调用的效果由同一来源提供给绑定和合法性。历史运行包可按已封存的 ABI 加载，历史编译证明按签发版本重放。

已有的单数组递推可沿用同一编译入口。中端从 F4 复核循环回边和调用端口，发布融合策略及绑定 CPU 的执行计划。指定核数会生成待测候选。自动选型缺少可比成本时采用原执行。`scar run` 只在显式试跑或同一入口通过测量准入后挂接候选。

原生 `compiler-plan.json` 锁定规划问题、计划和各项证据。`scar compile --plan` 在独立进程重放交付并核对锁定用例。发布 wheel 时先生成源码分发包，再从该分发包构建，以便打包输入与当前源码版本一致。

分阶段运行时，`scar build --manifest` 发布结果及 `graph-report.json` 的双向引用。`scar plan --graph` 核对各工件角色、重新确认源锁并使用已有图，发布改写、硬件成本和封存计划。`scar compile --plan` 消费该计划，重新验证排程、生成工程并比对锁定输入的结果。同一目标用 `scar compile --manifest` 可串接三阶段。C++20 构建前后检查同一组源码和链接输入的身份，事务提交时复验内容。

## 3. 后端

| 层 | 功能 | 输入 | 交接产物 |
| --- | --- | --- | --- |
| 交付选型 | 重读并校验引用，重组规划问题，独立核验所选排程及 CPU 可用性 | 锁定请求、图改写、成本和排程 | `project/delivery.json`，含已采用的排程、CPU、源请求和可执行文件摘要 |
| C++20 降级 | 按编译单元生成 C++20 源码及其编译参数，保留本地头文件和必要的原生库 | 已选源码修订及其按单元记录的编译参数 | `project/cpp20-inputs.json` 绑定计划、生成源码、头文件、编译选项和绝对路径链接输入 |
| 构建与链接 | 构建独立工程，核对二进制、依赖和已绑定的跨语言目标符号 | 已生成源码、CMake 输入、原始调用图 | `project/CMakeLists.txt`、可执行文件、构建日志、ELF 依赖和符号核验记录 |
| 验证 | 对照原版与生成版的退出状态和输出，按声明合同比较 | 两个可执行入口、同一输入和 CPU 配置 | `validation/` 的原始输出，以及 `result.json` 的逐用例正确性和计时 |

原生源码适配器应用已准入的改写并交出 C++20 编译单元、编译选项和链接输入。C/C++ 生成工程按原编译单元的宏设置保留断言行为。Fortran 方言和 ABI 转换归源语言适配器处理。显式形状和 assumed-size 的 `BIND(C)` 数组支持列主序原位访问。固定秩、原始数值类型的 assumed-shape 标量元素访问使用 GNU CFI 描述符，保留下界、空维和有符号步长。类型验证覆盖 CFI 构造、降秩切片和非拥有型指针关联。固定秩 `CONTIGUOUS` 跨步实参按 GNU ABI 打包，正常返回时按 `INTENT` 决定写回。拥有型描述符分配和释放仍需独立的生命周期合同。

C++20 后端集中在 `compiler/backend/cpp20.py`，负责计划重放、工程生成、循环区域降级及产物检查。`compiler/qualification.py` 独立运行锁定用例并保留校验与计时证据。Python 目前实测覆盖可证明的循环区域。未绑定调用、完整入口副作用和一般区域改写仍待覆盖。

标量样本的内部采集入口为 `python -m scar.runtime.scalar_observe --selection FILE --out FILE`。根据选择工件的 schema 分派，同一入口共用原程序启动、监控清理和表快照。

后续增加源语言沿用图与证据接口。新增 GPU 资源、传输与算子实现通过 `PlanningProblem` 和可重放的执行计划进入中端。C++20 交付消费计划选定的实现和资源绑定，并通过算子 ABI 接入外部高性能库。

## 共享职责

`ir/` 定义图、数据、状态与计划类型。调用出口、编译器符号、源码字节、执行观测等类型和紧邻的查询按职责归并。前端的静态分析、观测关系和跨区域依赖查询分别归入 `analysis/static/`、`analysis/observed/`、`analysis/dependencies/`。`artifacts.py` 统一管理工件摘要、原子发布和证据表读写。证据表以相对路径、压缩与解码摘要、字节数及记录数作为交接合同。图查看由 `visualization/` 独立提供。构建证明记录分析实现摘要，历史源码保存在 Git，已有产物可按对应版本回读或重新构建。

## 持续验收

CPU 清单分别验证 F0–F5、硬件拓扑、M1–M3 和 B1–B2。真实混合方言目标跨进程交换图、计划和 C++20 项目。任一判据未收集到有效测试、时序或资源验证失败、原版与生成版输出不同，均会阻止发包。 [CPU 验收清单](../gates/cpu.json)
